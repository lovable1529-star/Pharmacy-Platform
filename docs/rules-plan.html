Karsons Pharmacy Platform · Engineering plan

Making the clinical rules configurable

What exists, what is quietly broken, and what it takes to put the decision logic in Muka's hands — checked against his own two specifications and against the live database rather than against the code alone.

01 · Position

The engine is good. Nothing else is.

The decision engine itself is the strongest part of the codebase. It is pure — no database, no clock, no network — so it can be replayed against any historical submission. It evaluates every rule rather than stopping at the first match, records a full trace of what it considered, and treats a rule whose field is missing as skipped rather than passed. That last decision is what stops a blank answer from satisfying a safety check.

Around it, three things are missing or wrong.

WhatStateConsequence
Rule authoring UI Does not exist The designer edits questions only. The one UI path to a ruleset is duplicating a service that already has one, which copies rules verbatim. Nobody can write or change a rule.
Rules per service 1 of 3 Only Weight Management — Repeat Request has a published ruleset. Flu and first-consultation take no automatic view at all.
Two derived inputs Never computed Four of the 24 GLP-1 rules silently skip on every submission — including both routes to GREEN. See below.
Found while checking this plan

On submission, deriveValues() is called with the form's own answers, height, weight and date of birth — but never with the patient's previous weight or previous strength. So derived.weightLossPercent and derived.doseStepChange are always null, and every rule that reads them is skipped.

RuleOutcomeNeedsWhat it was for
dose-skip RED doseStepChange “No skipping strengths — only same or ±1.” His matrix marks this Block. It has never fired.
stable-continue GREEN weightLossPercent The main auto-approve path — ≥2% loss, good suppression, no snacking.
increase-supported GREEN doseStepChange The other auto-approve path.
weight-loss-below-target AMBER weightLossPercent 0–2% loss — suggest considering an increase.

Both GREEN routes are dead. With neither able to fire, every repeat request falls through to the ruleset's default — which is AMBER, by his own instruction. The tool is therefore safe, and completely unable to do the thing he asked it to do:

“Reduce pharmacist workload by auto-triaging requests into GREEN (auto-approve), AMBER (review), or RED (block).”

A pharmacist reviews one hundred per cent of requests today. Nobody would notice from the screen — the queue simply looks busy.

02 · Mandate

He already asked for this, in writing

The scope of work lists among its deliverables:

“Admin guide for maintaining Config (age limits, thresholds, advice text).”

He expects to change age limits, thresholds and advice wording himself. Today every one of those is a code change and a deploy.

More usefully, the specification tells us exactly what shape the editor should be. Section 5 and the Decision Matrix are not prose — they are seven tables, all in the same four columns:

Input · Condition · Outcome · Notes

That is the interface. He has already designed it; we should build the thing he wrote rather than invent a rule-builder abstraction and then teach it to him. The seven groups — eligibility, dose, supply length, BMI, missed doses, adverse effects, supportive checks — become the editor's sections.

03 · Design

What gets built

The condition builder is bound to the form

The field picker offers only what that service's published questionnaire actually collects, plus the calculated values available to it. It is not a free text box, so a rule can never reference a question that does not exist — which is the failure mode that produced the four dead rules and would otherwise reappear the moment a question is renamed.

Operators come from the engine's existing set, worded for a pharmacist rather than a programmer:

Reads asEngineUsed in his matrix for
is / is noteq · neqPregnancy, dose request, consent
is one of / is none ofin · ninAdverse effect severity, suppression bands
is above / is undergt · lt · gte · lteAge limits, BMI, hydration, weeks on dose
is betweenbetweenBMI 23–24.9
was answered / was not answeredexists · notExistsNotes, questions for the pharmacist
all of / any of / notall · any · notEvery compound row in the matrix

Outcomes are not only a colour

His matrix produces four different kinds of result, and the engine already carries all four — they just have no editor:

  • Outcome — GREEN, AMBER, RED. Worst wins, always.
  • Message to the pharmacist — why this fired.
  • Message to the patient — never a dose instruction.
  • Advice — non-blocking, appended to the summary and printed on the back of the prescription. His hydration and BMI congratulation rules are this kind, not a triage decision.

Advice-only rules need a fifth pseudo-outcome in the editor so a rule can attach guidance without moving the colour. The engine supports it today by giving a GREEN rule an advice string; the editor should present that as its own thing rather than making him understand the trick.

Versioning mirrors the form exactly

Draft, publish, immutable version, submission bound to the version that judged it. All of that already exists in the schema — ruleset_version is versioned per service and rule_evaluation records which version decided each submission. The editor writes drafts and publishes; it does not need new tables.

The simulator is the reason the engine is pure

Before publishing, replay the draft ruleset against every historical submission for that service and show what would change:

// Replaying draft v2 against 148 past submissions
  GREEN → AMBER     3   tighter BMI band
  AMBER → GREEN    22   weight-loss rule now firing
  AMBER → RED       1   dose-skip now firing
  unchanged       122
                    → 22 requests a pharmacist would no longer review

This matters more here than on a typical project because his own specification is openly provisional — “It's not 100% perfect”, and the thresholds are his best guess at numbers he has never been able to test. Replay turns tuning from a gamble into a measurement, and it is the single feature most likely to make him feel the tool is his.

04 · His open question

Scoring, or discrete rules?

From the specification:

“Is it better with a scoring system (0–5) throughout the tool, with points adding up to outcomes?”

Recommendation: both, split by purpose. Not a compromise — the two halves of his matrix are genuinely different kinds of judgement.

KindExamples from his matrixMechanism
Absolute
never scored		 Pregnancy · age outside licence · severe adverse effect · ≥2 missed doses · BMI <23 without a decrease · dose skip Discrete rules. A single trigger decides on its own and cannot be outweighed by good scores elsewhere.
Judgement
scored		 Suppression + snacking + weight loss + hydration → continue, increase, or decrease A score, banded into an outcome and a recommendation.

The danger in a pure scoring model is exactly the thing his tool exists to prevent: a pregnant patient with excellent suppression, perfect hydration and 4% weight loss accumulating enough points to clear a threshold. Safety limits must be non-negotiable, and the engine's worst-wins ordering already guarantees that a RED cannot be outvoted.

Implementing the scored half needs one new calculated value — score, summing weights the editor exposes per answer — and then ordinary band rules written on it. No engine change; a new DerivedCalculation and a weights table in the editor.

Decision needed from Muka

Scoring is Phase 4 and it is the one part of this plan I would not build until he has used the discrete editor against real requests for a few weeks. His instinct may be right, but the weights can only be chosen from data he does not have yet — and the simulator is what will produce it.

05 · Sequence

Four phases

00

Feed the engine what it is missing

~half a day

Independent of the editor, and it should go in regardless. Pass the patient's previous weight and previous strength into deriveValues() at submission, so weightLossPercent and doseStepChange stop being null.

  • Read the last completed supply for the patient before deriving.
  • Revives both GREEN routes and the dose-skip RED block.
  • Add a test proving a rule on a missing field is skipped and does not pass — the current behaviour is right and must stay right.
  • Backfill: re-evaluate historical submissions so the simulator has an honest baseline to compare against.
01

The rule editor

~5–7 days

The core deliverable: his decision matrix, editable, per service.

  • Rules list grouped by his seven categories, with drag-to-reorder for priority and a per-rule on/off switch.
  • Condition builder bound to the published form's real question IDs and calculated values; nested all / any / not.
  • Outcome, pharmacist message, patient message and advice per rule.
  • Draft autosave, then publish as the next immutable version.
  • Validation before publish: unreachable rules, rules referencing a question the current form no longer asks, and a ruleset with no default.
02

The simulator

~2–3 days

Replay a draft against real historical submissions and show the difference before anything goes live.

  • Counts by transition, plus a drill-down into the affected submissions.
  • Per-rule firing counts, so a rule that never fires is visible rather than assumed to work — which is precisely how the four dead rules stayed hidden.
  • Cheap because the engine is already pure: no new evaluation path, just a different source of context.
03

Rules for the other services

~1–2 days, plus his clinical input

Flu is genuinely simple and its specification already lists the questions: fever in the last 24 hours (clinician-answered on the day), currently unwell, flu vaccine within six months, pregnancy, allergies. Two or three RED rules and an AMBER default would cover it.

  • Authored by him in the new editor — the first real test of whether it works.
  • Vaccine → batch and expiry auto-fill is already supported by option metadata in the form schema; it needs configuring, not building.
04

Scoring, if he still wants it

~3–4 days

Deliberately last. A score calculated value with editable weights, banded by ordinary rules, and absolute safety rules still winning outright. Decide after Phase 2 has produced real data.

Total

Phases 00–03 land the thing he actually asked for in roughly nine to thirteen working days. Phase 00 alone is half a day and is the difference between a tool that auto-approves and one that sends everything to a pharmacist.

06 · Before starting

What I need from him

QuestionWhy it blocks
Should weeks on current dose come from the patient's answer or from our own supply record? His matrix leans on it for nearly every dose and supply rule. Self-reported is gameable, and he explicitly worries about patients circumventing checks. Our record is authoritative but only once repeat care has been running.
Who may publish a ruleset — owner only, or any pharmacist? Publishing changes clinical behaviour for every subsequent patient. It should be a named permission, and my assumption is owner-only unless he says otherwise.
Confirm “Block” and RED are the same thing. His matrix uses both words. The code treats them as one: refuse, advise, redirect to booking. Worth confirming rather than assuming.
Flu rules — his clinical call, not ours. I will not invent vaccination rules. Phase 03 needs him for an hour.
One thing to be candid about

The four dead rules were not caught by 30 passing tests, because the tests exercise the engine with values supplied directly — they prove the logic, not the wiring that feeds it. Phase 02's per-rule firing counts are the durable fix for that class of problem, which is a good reason not to treat the simulator as a nice-to-have.
