01

Decide the database region — do this first

Do this before anything else

The live Supabase project is in Seoul (ap-northeast-2). Your client is on the Isle of Man. Every query on every page crosses half the planet and back.

This is measured, not guessed. From the development machine on 29 August:

OperationCostTimes per page load
Postgres round trip~180 ms5
Supabase Auth call210–410 ms2
First connection of the day~1.4 s1

That accounts for essentially the whole of a two-second page. It is not query cost and it is not rendering — it is distance. Moving the project to London (eu-west-2) cuts every one of those trips to roughly 20–40 ms, which turns a two-second screen into a three-hundred-millisecond one. No amount of code will do that.

It is also the right home for the data regardless. Isle of Man patient records sitting in South Korea is a conversation you do not want to have with a pharmacy owner, and .env.example in this repo has said eu-west-2 from the beginning — the live project was simply created somewhere else.

What moving involves

Supabase cannot change a project's region in place. You create a new project and re-run the setup, which you already do by hand:

  1. You — new Supabase project, region London (eu-west-2). Save the database password.
  2. Run 01_schema.sql through 14_prescription_numbers.sql in order in the SQL editor. All fourteen, ascending, no skips.
  3. You — create your staff login and seed, exactly as in SETUP.md sections 6 and 7.
  4. Take the new connection strings and keys into step 04.

Budget an hour, and do it well before the demo rather than the night before. If you would rather not, everything below still works against Seoul — the demo will simply feel like a two-second application instead of a fast one.

If you stay on Seoul

Set the Vercel function region to Seoul (icn1) in step 05 instead of London. Putting the functions in London while the database is in Seoul is the worst of both worlds — you would add a second intercontinental hop to every query.

02

Finish the database

Whichever project you are deploying against, one script has not been run yet.

Outstanding

platform/supabase/14_prescription_numbers.sql has never been run. Until it is, every prescription PDF is numbered UNNUMBERED-…, because the function that allocates a real per-branch, per-year number does not exist.

Open Supabase → SQL Editor, paste the file, run it. It is written to be safe to run more than once, and it ends with a verification query that should return 1 in all four columns:

sequence_table | number_column | unique_guard | allocator
             1 |             1 |            1 |         1

If you are setting up a fresh London project, run all fourteen in order instead — 14 depends on tables created by the earlier ones.

Confirm the two connection strings

Supabase gives several. Only two matter, and mixing them up produces errors that look like nothing to do with connection strings:

VariablePortUsed forIf you get it wrong
DATABASE_URL 6543 The application. Pooled through pgBouncer. On 5432 you get prepared statement "s1" already exists, intermittently.
DIRECT_URL 5432 Migrations from your own machine. On 6543 migrations fail with syntax or permission errors.
03

Import the repository into Vercel

  1. Go to vercel.com/new and sign in with GitHub.
  2. Import Pharmacy-Platform. If it is not listed, grant Vercel access to the repository from the GitHub connection screen.
  3. Set Root Directory to platform. This is the one setting that is easy to miss and guarantees a failed build — the Next.js app is not at the repository root.
  4. Leave Framework Preset, Build Command and Output Directory on their detected values. Vercel finds pnpm-lock.yaml and uses pnpm on its own.
  5. Do not deploy yet. Add the environment variables first — see the next step. A deploy without them fails at build time on DATABASE_URL is not set.
Node version

There is no .nvmrc and no engines field, so Vercel picks its current default (Node 22 at time of writing), which matches local development. Nothing to configure.

04

Environment variables

Vercel → Settings → Environment Variables. Tick Production, Preview and Development for each unless noted, otherwise a preview deployment comes up with an empty configuration and looks broken.

Required for the demo

These five are the whole demo. Nothing else on this page is needed to sign in and show the clinical screens.

VariableWhat it does, and what happens without it
DATABASE_URL Required Every query the app makes. Port 6543. Missing, the build fails outright with a message telling you so.
NEXT_PUBLIC_SUPABASE_URL Required Where sign-in goes. Missing, nobody can authenticate.
NEXT_PUBLIC_SUPABASE_ANON_KEY Required The browser half of authentication. Safe to expose — it is the public key, and Row Level Security is what protects the data behind it.
NEXT_PUBLIC_APP_URL Required Your production URL, no trailing slash, e.g. https://karsons.vercel.app. This one fails silently. Unset, it falls back to http://localhost:3100, and every booking link, payment link and staff invitation points at a machine that is not there.
SUPABASE_SERVICE_ROLE_KEY If inviting Only needed to invite staff users. Without it the Users screen says so plainly and everything else works. Never prefix this with NEXT_PUBLIC_ — it bypasses every security rule in the database.
Silent failure

NEXT_PUBLIC_APP_URL is the one to double-check. Nothing errors, nothing logs, and the application looks completely healthy — the links are simply wrong, and you find out when you click one in front of the client.

Not needed on Saturday

Leave these unset. Each one is designed to fail quietly and stay out of the way rather than break the app.

VariableBehaviour while unset
RESEND_API_KEY, EMAIL_FROM Skip Email logs what it would have sent and reports "Email is not configured yet." Nothing crashes.
TWILIO_* Skip SMS and WhatsApp queue as UNAVAILABLE and send later if keys ever arrive. Nothing is lost.
CRON_SECRET Skip All four scheduled jobs refuse to run. See Switched off for now.
STRIPE_* Skip Payments are simulated by design. Out of scope until the NMS and GPhC position is settled.
DIRECT_URL Skip Migrations run from your machine, not from Vercel. It does no harm to add it, and no good either.
CLINIC_ALERT_EMAIL, PHARMACIST_WHATSAPP_TO Skip Alert destinations. Irrelevant while email and SMS are off.
05

Put the functions next to the database

Vercel → Settings → Functions → Function Region.

If your Supabase project is in…Set the function region to
London (eu-west-2) — recommendedLondon, UK (lhr1)
Seoul (ap-northeast-2) — currentSeoul, South Korea (icn1)

The rule is simply that the server code and the database should be in the same place. Every page makes five database round trips and two auth calls; if the function is in London and the database in Seoul, all seven cross the world twice. Matching them is free and is worth more than any code change.

The default region is Washington DC, which is the wrong answer in both cases. Change it before the first real deploy.

06

Tell Supabase about the new address

Supabase only redirects back to URLs it has been told about. Until this is done, signing in appears to do nothing at all.

Supabase → Authentication → URL Configuration:

  • Site URL — your production URL, e.g. https://karsons.vercel.app
  • Redirect URLs — add both:
https://karsons.vercel.app/auth/callback
https://karsons.vercel.app/**          ← covers preview deploys and password reset

Keep http://localhost:3100/** in the list as well, so local development carries on working.

07

Deploy, then prove it works

Trigger a deploy — Deployments → Redeploy, or push any commit. Then walk this list. It is ordered so that a failure tells you which step above to go back to, and it remembers what you have ticked.

Expected

On London, first load of a screen should land in roughly a third of a second and a repeat visit should be immediate. On Seoul, expect around two seconds every time — working, but visibly slow.

When something is wrong

What you seeWhat it actually is
Build fails, no Next.js app foundRoot Directory is not platform.
Build fails on DATABASE_URL is not setVariables missing, or added after this deploy began. Redeploy.
Sign-in does nothingRedirect URLs not added in Supabase. Step 06.
No staff account exists for …You signed in with an email that has no app_user row. Re-seed with SEED_ADMIN_EMAIL and SEED_ADMIN_AUTH_ID.
Signed in, but every list is emptyThe same thing, seen from the other side: Row Level Security is working correctly and there is no app_user row for your auth ID.
prepared statement "s1" already existsDATABASE_URL is on port 5432. It must be 6543.
Every page takes about two secondsFunctions and database are not in the same region, or both are in Seoul. Steps 01 and 05.
Prescription numbers read UNNUMBERED-…Script 14 has not been run. Step 02.
Emails and texts never arriveExpected — they are switched off. Nothing is broken.
A screen shows data that is a few seconds out of dateThe 30-second route cache, and only for changes made outside the app. Anything done in the app clears it immediately.

Vercel's Logs tab shows server errors with the same digest the browser displays, which is the fastest way to turn "Application error" into an actual stack trace.

§

Deliberately switched off

None of this is needed for the demo, and none of it is missing work. It is built and waiting on decisions or credentials.

The four nightly jobs

platform/vercel.json already schedules them: appointment reminders at 09:00, the GP batch at 18:00, the daily summary at 18:30, and an audit-chain check at 02:00.

They will not run, and that is correct

Every cron route is guarded by CRON_SECRET, and the guard fails closed — with no secret set, all four return 401 and do nothing. That is the intended state for now: these endpoints are reachable from the public internet, so an unguarded one would let anybody trigger GP notifications.

To switch them on later: set CRON_SECRET to a long random string in Vercel. Vercel sends it automatically as a bearer token; you do not wire anything up. Email needs to be configured first, or the jobs will run and have nothing to send through.

Email, SMS and WhatsApp

Resend for email, Twilio for the rest. Email needs SPF, DKIM and DMARC aligned on the sending domain before @gov.im addresses will accept anything — GP surgeries are the recipients that matter, and they drop unaligned mail silently.

Payments

Simulated end to end. The flow is real — a payment link, a settle step, a status that moves to PAID, a notification queued — but no money moves and no card details are handled. Demonstrate it as the workflow it is; the Stripe integration waits on the NMS and GPhC position.

§

On the day

  • Open the five screens once before he arrives. The first request of the day pays about 1.4 seconds to open a database connection, and the first hit on each route compiles it. Both are one-off; do not let him watch you pay them.
  • Use the Vercel URL, not localhost. A development server is roughly ten times slower than the deployed build, and the difference is obvious to anyone watching.
  • Move between screens more than once. The second visit is where the caching shows — going back to Appointments after Patients should be instant, with no flash at all.
  • Mark someone arrived, then open Consultations. It shows the screens are joined up, and it is the exact thing that used to be broken.
Worth saying out loud

If the region move has not happened yet and he remarks on the speed, it is a straightforward answer: the database is currently in the wrong part of the world, moving it is an hour's work, and it makes every screen roughly five times faster. That reads as competence. Being vague about it does not.
