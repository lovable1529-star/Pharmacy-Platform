Part 01

The design system, applied across the platform

The Claude Design canvas was built on the palette the codebase already had — identical hex values for the brand ramp, the clinical colours and the neutrals. So this was not a reskin. It was token additions, a consolidation of duplicated patterns, and per-screen refinements.

Measured after the fact: of the 35 colours the canvas introduced beyond what the app already had, 32 were dark-theme values. In light mode it introduced exactly one new visible colour — a navigation surface a half-step off white. That is why the light theme looks familiar, and it should have been said in the first sentence rather than discovered later.

A dark theme that no component knows about

A complete second palette under data-theme="dark". Only token values change. Two things are deliberately not straight inversions: the brand ramp flips direction, so brand-700 goes from dark purple to pale purple and text-brand-700 on bg-brand-100 keeps working untouched in both themes; and the clinical colours stay unmistakably green, amber and red rather than being harmonised toward the brand. A pharmacist has to read RED as stop at a glance in either theme, and that outranks visual harmony.

The theme resolves in a blocking inline script before first paint, from the saved preference or the OS setting. Not a prefers-color-scheme media query — if the CSS also reacted to the OS, somebody who chose light would be flipped to dark the moment their laptop dimmed at dusk.

Consolidation

  • ~190 hard-coded corner radii across 44 files swept onto two named tokens.
  • A shared vocabulary — Panel, StatCard, Tag, Notice, EmptyState. All existed already, written slightly differently on each screen; four separate files had each invented their own amber pill.
  • The navigation regrouped into Clinical, Operations and Administration. Thirteen destinations in one flat list was a wall.

An accessibility bug found on the way

Fourteen files styled inputs with focus:outline-none, which applies on :focus — including :focus-visible. Those fields were cancelling the global focus outline, leaving a faint border change as the entire keyboard-focus indicator. All now carry a proper focus ring.

Part 02

The form designer, rebuilt

The old layout stacked an outline above the live preview inside one scroll container, with a palette rail and an inspector either side. Four regions — and the two that mattered, the question being edited and the effect of editing it, were the two furthest apart.

Three columns now: steps, the outline edited in place, and the real patient form pinned beside it. Selecting a question expands its row into its own editor rather than filling a panel on the far side of the screen.

  • The eighteen-type palette became a search field that matches on the hint as well as the label — which is why typing “weight” finds Measurement.
  • Follow-ups appear twice, deliberately: as a branch of the outline tagged with the answer that triggers it, and inside the parent's editor arranged by answer. The tree is for seeing the logic; the editor is for changing it.
  • Branch tags read the answer's own wording — if Other, never if option_3.

Every mutation is the same function it was, called from a different place. The preview is still the real FormWizard, so nothing can drift between what he builds and what a patient sees.

Part 03

Collapsing the sidebar gives the space back

Collapsing the rail moved 176px of screen into the left and right margins and the content stayed exactly as wide — a fair description of nothing happening.

The shell now sets --nav-freed on the content column and each page adds it to its own cap: calc(1080px + var(--nav-freed, 0px)). Additive rather than one shared maximum, because a patient record should not become as wide as an inventory table just because there is room. The 0px fallback is load-bearing — these containers also render in the patient-facing layouts, which have no sidebar and never set the variable.

The separate Collapse button is gone. The K mark toggles the rail, cross-fading to a chevron on hover so it reads as a control. One tradeoff: some people expect a logo to link home. Today is the first nav item, so home is one click away.

Part 04

Naming a step

Adding a step produced “Step 4”, “Step 5” … and the generated name was the only name.

The step name in the outline header is now the field itself — a heading at rest, a border on hover, a focus ring when you are in it. A new step arrives already focused with its name selected, so typing replaces it. Double-clicking a step in the rail renames it, because the rail is where you see the name and therefore where you will try to change it.

An emptied name falls back to its position — on blur, not on every keystroke, or clearing the field to retype would fight you by refilling as you delete.

Part 05

The consent question could not be configured at all

Three separate faults behind one report, and the first instance of the pattern that the later audit was built to find.

  • The clauses had no editor. They live on the schema, not the field — deliberately, so the wording is versioned and it stays provable what a patient agreed to. The designer edits fields, so it never saw them. The flu form ships ten clauses; none could be touched except by hand-editing JSON.
  • The tick-box wording was a string literal inside the control. The one sentence a patient actually signs was the one sentence the pharmacy could not change.
  • consentList was not in the palette at all — so a new service could never have a consent step, and “build your own form for any service” quietly excluded the one question every clinical service needs.

Clause ids are stable and never reused: an id is what a stored submission points at to prove which wording was agreed, so renumbering on delete would quietly repoint old consents at new text.

Part 06

Pharmacist declarations, and consent that can differ per question

The two items Part 5 left open.

Declarations had the identical fault. They could not hang off a selected question the way consent does — they are not a question, belong to no step, and are ticked on the consultation screen — so they got the outline column to themselves, reached from the steps rail. The panel says plainly that they never appear on the patient's form, because the live preview beside it shows exactly that form and an editor whose changes never appear looks broken.

Per-question consent was a schema change, so the schema changed. FormField.consentClauses wins over the form-wide list when set; unset, the form-wide list applies exactly as before. The editor states which list is in force before you edit it, because the two look identical and editing the wrong one silently changes another question.

The resolution became a tested function rather than an inline fallback. The test that earns its place: an empty list on the question is a deliberate “show nothing”, not a missing value. A || where a ?? belongs would make a question the pharmacy had explicitly cleared inherit ten statements again — looking perfectly fine on screen while recording agreement to text the patient never saw.
Part 07

The systematic audit

Five faults had been found one at a time, all the same shape: something the seeded forms use that the designer cannot reach. Rather than wait for the sixth, the whole surface was enumerated.

Three mechanical comparisons — every schema property against every property the designer writes; every field type against the palette and the renderer; every link against the routes that exist — then each gap weighted by how many times the real seeded forms use it.

Part 08

Closing the four deferred gaps

The audit deferred four things with reasons. All four were then closed, and one turned up a latent crash.

The crash

validateField called new RegExp(rules.pattern) unguarded. An invalid pattern throws, and the throw takes down validation for the whole step — a patient would have met a crash rather than a validation message. Now caught and treated as no pattern: the wrong answer to let through, and far better than the alternative. Two tests pin it.

The other three

  • Visibility rules. Both halves are pickers, never free text — the value is built from the target question's actual answers, so a rule cannot point at an answer that does not exist. That failure is silent: the question simply never appears.
  • Per-option hidden data. The flu form carries an @gov.im mailbox on every GP surgery option — that is how a practice learns their patient was vaccinated, and it could not be seen from the designer, let alone corrected. A wrong address there fails silently. Values keep their type, so ladderIndex: 0 stays a number.
  • Limits. Only the limits that do something for a given type are offered, read off validateField rather than guessed.

How this was verified

  • tsc --noEmit clean throughout.
  • 297 of 297 tests passing, up from 291. The unchanged pass rate through Parts 1–3 is the evidence that no behaviour moved during the redesign.
  • All twenty staff and public routes compile and execute — the 307s come from each page's own getStaffContext() redirect, not from middleware, so every page module genuinely ran.
  • Dark-theme token flip confirmed live in the browser; zero bg-white, text-black or hex literals in any className, which is why dark mode works everywhere without per-screen work.
  • Both public patient forms render with no console errors.
Two things were not verified. A production next build was never run — another session holds the dev server on the shared .next directory. And every editor added in Parts 4 through 8 sits behind staff auth in client components: route compilation proves they compile, not that they render. None has been clicked.
