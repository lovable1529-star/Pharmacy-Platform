Test Plan & Cases

What to test, how to test it, and — most importantly — how to write up what you find so it can be fixed without a conversation.

Read this before you start

This is a clinical system. A bug here can mean a patient is supplied a medicine they should not have had, or refused one they needed. Anything touching the red / amber / green decision, the approval gates, or what a patient is told about their own treatment is P1 by default — report it even if you are not certain it is wrong.

Part 01How to report a finding

A report that cannot be reproduced cannot be fixed, and one without a screenshot usually starts an argument about what was actually on screen. Every finding needs all six of these.

  1. Reproduce it a second time before writing it up. If it only happened once, say so explicitly — that is useful information, not a reason to stay quiet.
  2. Screenshot the failure, showing the whole browser window including the URL bar. If the layout is wrong, include a second shot at a different window width.
  3. Write the exact steps, starting from a signed-out browser. Include the data you typed, verbatim — "a bad height" is not reproducible; 1.7 is.
  4. Say what you expected and what happened. Both. "It didn't work" tells the developer nothing about which of the two is wrong.
  5. Open the browser console (F12 → Console) and paste any red errors. Do the same for the Network tab if a request failed.
  6. Note the time, to the minute, and the branch you were working in. Server logs are searchable by time.
Video beats prose for anything intermittent

If something only fails sometimes, or depends on timing, record a short screen capture instead of describing it. Intermittent faults are the ones most often closed as "cannot reproduce" — a recording prevents that.

What counts as a finding

Anything that is wrong, confusing, or that you had to think twice about. Wording that misleads a patient is a defect in a clinical system, not a nitpick. So is a button that looks disabled but is not.

Part 02Severity, and what it means

LevelMeansExamples in this system
P1 Patient safety, or data that cannot be recovered A red request can be approved · a green is produced from figures nobody could have · a medicine name reaches an SMS · one patient's data appears on another's record · an audit entry is missing
P2 A journey cannot be completed, or money is wrong The form cannot be submitted · a prescription strands with no way forward · the wrong price is charged · a required leaflet can be skipped
P3 Wrong but workable, or cosmetic Misaligned layout · a count that is out by one · unclear wording that does not mislead · a slow page

If you are unsure between two levels, choose the higher one and say you were unsure. Triage is cheap; a missed P1 is not.

Part 04Known limitations — please do not report these

  • Payment is a tickbox. Nothing takes card details. This is the client's decision, not an oversight.
  • Rules can be tuned, not created or deleted. Changing a threshold, outcome, priority or message works; adding a new rule does not exist yet.
  • The face-to-face page is a placeholder and says so on itself. Its opening hours and phone number are deliberately not real.
  • Branding values are placeholders until the client supplies real ones.
  • Long lists are not paged. Known, and owed.
  • Demo patients cannot be deleted. Clinical records never can be — that is a design rule, not a missing feature.
  • Prices apply from now on. Anything raised before a price was set will not retrospectively acquire one.

If one of these looks differently broken from how it is described here — say, the placeholder page 404s rather than rendering — that is a finding.

Suite AAccess and permissions

A-01A signed-out visitor cannot reach any staff screenP1
Steps
  1. Sign out, or open a private window.
  2. Visit each in turn: /, /patients, /repeat-care, /services, /reports, /compliance, /users, /inventory, /payments.
Expected: every one redirects to /sign-in. None briefly renders content before redirecting.

Watch for: a flash of real data before the redirect. Screenshot it if you see one — that is a P1.

A-02A lower-privileged role cannot do a pharmacist's jobP1
Steps
  1. Sign in as Reception or Viewer.
  2. Try to reach /services/weight-management-repeat/rules and press an edit control.
  3. Try to approve a repeat request.
  4. Try to remove a service.
Expected: each is refused. A refusal that only hides a button is not enough — if you can reach the URL directly, the server must still say no.
A-03Signing out actually ends the sessionP2
Steps
  1. Sign in, open a staff page, copy the URL.
  2. Sign out.
  3. Press the browser Back button, then paste the URL into the address bar.
Expected: both attempts land on sign-in. Cached page content may flash from the browser's own history — note whether real patient data is visible if so.

Suite BNew-patient form

B-01Choosing "see someone in person" stops the form and offers a way outP2
Steps
  1. Open /f/weight-management-first signed out.
  2. Choose I would rather see someone in person.
Expected: a stop message appears with a See the face-to-face programme button below it — not overlapping the text. The remaining nine steps do not appear.

Then: press the button. It should reach a page that openly identifies itself as a placeholder, with a link back to the form.

B-02An implausible measurement is refused at entryP1
Steps
  1. Choose Continue online and work to Your measurements.
  2. Enter height 1.7, weight 84, waist 95. Try to continue.
  3. Repeat with height 170, weight 13.
  4. Repeat with waist 34.
  5. Finally enter height 170, weight 84, waist 95.
Expected: each of the first three is refused with a message naming the field. The fourth is accepted.

Also try: switch the units to feet/inches and stones, and enter a genuine value like 5 ft 7 and 13 st 3. That must be accepted — if imperial answers are rejected, that is a P1 regression.

B-03Required leaflets cannot be skippedP2
Steps
  1. Work through to the Consent step.
  2. Without ticking "I have read this", try to submit.
Expected: submission is refused and the unticked leaflet is highlighted. Ticking it allows submission.
B-04Answers survive closing the browserP2
Steps
  1. Fill in the first three steps. Wait for "Answers saved".
  2. Close the tab entirely. Reopen the same URL.
Expected: the answers are still there. Note precisely what is lost if anything is.
B-05Every required field is genuinely requiredP2
Steps
  1. On each step, try to advance with everything blank.
  2. Note any field marked with an asterisk that lets you past.
Expected: every asterisked field blocks, and the message names the field rather than saying "check your answers".
B-06Uploads accept what they should and refuse what they should notP2
Steps
  1. At Evidence and safety, upload a normal JPG and a PDF.
  2. Try a very large file (over 20 MB) and an unusual type (.exe, .svg).
Expected: valid files attach and are listed. Refusals say why. Nothing fails silently, and nothing hangs with a spinner that never resolves.
B-07The thank-you screen hands over a tracking linkP3
Steps
  1. Submit a complete form.
  2. Read the confirmation. Follow the tracking link.
Expected: the confirmation does not promise an appointment. The link opens a page showing the request as received.

Suite DTriage and decision gates

This suite is the heart of it

Every case here is about the system refusing to do something. Test each one by trying to get past it, including by editing the URL. A gate that only hides a button is not a gate.

D-01A red request cannot be approvedP1
Steps
  1. Open Sinead Corlett's red request.
  2. Try to approve it with no note.
  3. Try again with a long, confident note.
Expected: refused both times, with a message saying it must go through the urgent list or be declined. No wording in the note may unlock it.
D-02An amber cannot be approved without reasoningP1
Steps
  1. Open Peter Cregeen's amber request.
  2. Approve with the note box empty.
  3. Approve with only whitespace in the note.
  4. Approve with a real sentence.
Expected: the first two are refused; the third succeeds. Whitespace must not count as reasoning.
D-03A new patient cannot be approved before the callP1
Steps
  1. Open a new-patient request with no recorded call.
  2. Try to approve.
  3. Record a call with outcome "no answer". Try again.
  4. Record a completed call without ticking identity verified. Try again.
  5. Record a completed, identity-verified call. Try again.
Expected: only the last attempt succeeds. Steps 2–4 are each refused with a message explaining what is missing.
D-04A nonsense measurement cannot be authorised onP1
Steps

Ask a developer to place a request whose stored height is 1.7 (the entry form now blocks this, so it has to be seeded). Then:

  1. Open it and read the RAG outcome and trace.
  2. Try to approve it, with and without a note.
Expected: the BMI rules show as skipped, and approval is refused with a message about the figures not reading as a real measurement — whatever colour the engine reached. A note does not clear it.

Why this matters: before this was fixed, a height typed in metres produced a BMI of 290,000, which satisfied the "BMI at least 25" condition and came back green.

D-05Two people deciding the same request do not overwrite each otherP2
Steps
  1. Open the same request in two browsers, signed in as two different staff.
  2. Approve in the first.
  3. Approve in the second.
Expected: the second is refused or clearly reports that the request has already moved. It must not silently create a second prescription.

  2. Approve one request of each kind and compare the payment raised.

Suite HPatient tracking and referral

H-01The tracking page shows stage and nothing clinicalP1
Steps
  1. Submit a request and follow its tracking link.
  2. Read every word on the page.
  3. Have staff move the request forward (approve, prescribe, dispatch), refreshing the page after each.
Expected: the stage advances. At no point does the page name a medicine, a dose, a BMI, or a red/amber/green colour. Anything clinical appearing here is a P1.
H-02A tracking link cannot be guessed or probedP1
Steps
  1. Take a working tracking URL. Change one character. Load it.
  2. Try /track/test, /track/1, /track/.
Expected: all give the same not-found response. A near-miss must not behave differently from nonsense — a different error would confirm the token was nearly right.
H-03A draft that was never sent says soP2
Steps
  1. Start a form, type enough for it to save, but do not submit.
  2. Open its tracking link.
Expected: it clearly says the form has not been sent yet. A patient waiting for a call on an unsent form is the worst version of this feature.

Suite JSecurity and abuse

J-01One patient's data never appears on another's screenP1
Steps
  1. Note the URL of one patient's record and of one submission.
  2. Substitute another patient's identifier into each URL.
  3. Get into the repeat form as Ruth, then change the resume token in the URL to another patient's.
Expected: refused or not-found every time. Any leakage across patients is the highest-severity finding in this document.
J-02Text typed by a patient cannot become markupP1
Steps
  1. In free-text answers, enter: <script>alert(1)</script>, <img src=x onerror=alert(1)>, and '; drop table patient; --.
  2. Submit, then view the answers as staff, in the drawer, in a PDF and in any message generated.
Expected: shown as literal text everywhere. No dialog, no missing content, no broken layout.
J-03An expired or reused link behavesP2
Steps
  1. Submit a form, then reload the resume link you used to fill it in.
  2. Ask a developer for an expired resume token and try it.
Expected: an already-submitted link says so rather than opening a blank form — which would create a second submission for one patient. An expired link explains itself and points at what to do.
J-04Repeated wrong attempts are not unlimitedP2
Steps
  1. At the repeat access gate, submit twenty wrong ID/email combinations quickly.
  2. Do the same at the sign-in screen.
Expected: record exactly what happens. If there is no limit at all, that is a finding worth raising even though nothing visibly breaks.

Part 05Exploratory charters

Scripted cases find the faults somebody thought of. These are for the ones nobody did. Spend a fixed 45 minutes on each, take notes as you go, and report anything surprising even if you cannot classify it.

CharterExploreLooking for
The impatient patient Double-click every submit and Next. Press Back mid-form. Refresh during an upload. Open the same form in two tabs. Duplicate submissions, lost answers, two prescriptions from one request
The interrupted pharmacist Start an approval, leave it 20 minutes, come back and finish. Have somebody else act on the same request meanwhile. Stale screens acting on old data; silent overwrites
The wrong units Switch between metric and imperial repeatedly, mid-entry, on every measurement. Values converted twice, or read as the wrong unit
The edge of the calendar Dates of birth today, in the future, in 1900, on 29 February. Expiries today and yesterday. Off-by-one errors, ages that go negative, expiries that pass
The awkward name Names with apostrophes, hyphens, accents and non-Latin script. Very long addresses. Broken display, truncation without warning, failed saves
The slow connection Throttle the network to Slow 3G in devtools and use the form. Lost autosaves, double submits, spinners that never end

Before you file it

Check it is not in Part 04. Then reproduce it once more from a clean browser. Roughly one report in five turns out to be a stale session or a half-completed earlier test — reproducing from scratch catches those before they cost anybody a morning.
